Port Task Routing Problem

What we are optimising, what the agent may do, and what it knows when it decides. Settled 28 August 2026. This page is a hand-written snapshot for reading and sharing, not a living document: the canonical copy is routing/docs/PROBLEM.md, and where the two disagree the Markdown is right.

01 Objective

Maximise XP per hour: the long-run average reward per unit time of a continuing process.

g = lim (T → ∞)  E[ total xp earned by T ] / T

This is a gain-optimal semi-Markov decision process. Actions have durations, decisions are made only in port, and there are no episodes. The handle is the ρ-parametrisation: for a candidate rate ρ, maximise the undiscounted sum of xp₃ − ρ·dt₃; the ρ at which that optimum is exactly zero is the optimal gain. Bisect on ρ.

Time in ticks (0.6 s, the game’s own quantum — integer arithmetic, no rounding drift). Reward in XP. Distance in game tiles is an input to the time model, never a state variable.

Level is not stationary

XP raises Sailing level, which changes both task capacity and which tasks and ports are legal. So g is a function of level, not a single number. Solve at a fixed level and treat the levelling curve as a sequence of such solutions — level moves slowly next to a task cycle.

A 190× spread in XP means which tasks you take dominates how efficiently you sail between them. The value is in the tail — which is the whole economic case for scouting.

Sailing requires the boat to be with you. Accepting does not — and that is the whole point.

05 Transitions

Automatic effects, in this order, whenever the player is in port p — on arrival and after any Accept:

  1. Load — every accepted task whose origin is p, boat present, joins L.
  2. Deliver — every loaded task whose destination is p: award XP, k += 1, drop from A and L.
  3. Reroll — if k == 8: redraw all 23 boards, clear O, set k = 0. A and L untouched.
  4. Reveal — if p has a board, write its true offers into O[p].

Reveal comes last so a delivery that triggers a reroll leaves you looking at the fresh board. Loading is checked after Accept too, so accepting an outbound task while the boat is already in port loads it immediately.

06 What makes this hard

It does not decompose into episodes

Treating one reroll cycle as an episode fails: A persists through the reroll, so the boundary is not a regeneration point. You can sit at k = 7, fill every slot from offers already scouted, then complete them across the boundary and start the next cycle several completions in, holding tasks the new offer set never contained.

“Eight completions per reroll” is an accounting invariant, not a planning budget.

Scouting perishes; accepted tasks do not

A reroll destroys every board you read. Accepting is the only way to carry what you learned across the boundary — and it needs no boat, which is exactly why teleport and accept pair up.

Near k = 7 that creates real pressure to fill every slot before the reroll burns your scouting. Against it, banking spends slots the fresh offers might have filled better. That trade-off should be discovered, not hand-coded.

Partial observability, and nothing else

The only hidden information is boards not yet read this epoch. The only stochasticity in the whole process is the reroll draw. Between rerolls, given full information, this is a deterministic prize-collecting pickup-and-delivery problem with a capacity constraint.

The prior is small and already in our data: an unread board is a uniform 8-subset of its known pool of about twenty. Every pool holds at least eight, so a full draw is always possible.

No deadlocks, no failure

There is always a legal teleport, so the agent can never be stranded without its boat. Voyages cannot capsize. Transitions are deterministic apart from the reroll.

Worth verifying once we have the teleport table: from every port there must be a teleport to some port with a shipwright.

07 What the solver has to be

  • Not exact DP. O alone is 23 boards drawing 8 from ~20, times read/unread flags, times positions, times A and L.
  • A real combinatorial solver for the deterministic core — branch and bound, beam search or CP over task selection and sequencing between rerolls.
  • Sample-based planning across rerolls — determinise the unread boards, solve, act, re-plan. Sampling a fresh O is precisely what the environment does, so simulator and planner share machinery.
  • The ratio objective via ρ-parametrisation, not optimised directly.
